# BLE pairing compared with other keyboard ports

Read-only research, 2026-10-02. No device, UI, serial, flash or transport changes. Repository snapshots are pinned below; a source comparison or maintainer report is not hardware validation of NocFree.

## Keep the two current failures separate

The owner-assisted host pairing attempt discovered the named keyboard and macOS accepted Just Works, then reported unmapped status `708` after 2.091 seconds. USB was subsequently absent on reattachment without reset; restarting that retained image returned normal USB. Those observations support investigating a transient runtime halt or failed task after pairing, but do not prove a panic, stack overflow, cryptographic failure, or host status meaning. [Pairing investigation](mac-ble-pairing.md).

The subsequent Warn-level USB logger image passed its exact recovery/readback checks but did not expose normal USB/CDC after startup. No CDC stream was opened and no new pairing attempt was made on it. That is a distinct startup regression/observation gap, not a reproduced pairing failure. Its size, memory placement, features and USB descriptor changes require comparison against the preceding working image before changing BLE security behavior.

## Exact differences worth recording

The Elytra [manifest](https://github.com/rmk-rs/rmk/blob/9607aedf343b17dd6b27307583ae80c4f728fbbd/examples/use_rust/nrf_dongle/central/Cargo.toml), [entrypoint](https://github.com/rmk-rs/rmk/blob/9607aedf343b17dd6b27307583ae80c4f728fbbd/examples/use_rust/nrf_dongle/central/src/main.rs#L62-L108) and [memory map](https://github.com/rmk-rs/rmk/blob/9607aedf343b17dd6b27307583ae80c4f728fbbd/examples/use_rust/nrf_dongle/central/memory.x) are the strongest same-chip baseline. The same one-central/one-peripheral capacity as our left does not identify a missing controller role flag. Its address derives from FICR DEVICEID; our address derives from FICR DEVICEADDR. Both set the random-static high bits. Different identity derivation alone is not proof of a pairing failure: changing it would change bond identity and could hide stale-state evidence. Preserve the current identity while diagnosing.

Neither the examined Elytra nor Cornix manifest requests host passkey entry or legacy pairing explicitly. Absence of a feature string is weaker than resolved-feature inspection; do not claim full generated defaults or actual host IO capability without inspecting the relevant framework revision. Our resolved stack already uses Cortex-M4 optimized LESC; macOS accepted its NoInputNoOutput/Just Works attempt. Enabling passkeys or legacy mode is not presently matched to a demonstrated refusal.

Cornix's [Cargo manifest](https://github.com/numachang/cornix-rmk-custom/blob/d5e7498bcd7f9c4861a26e587ad2d4e7842035be/Cargo.toml), [lockfile](https://github.com/numachang/cornix-rmk-custom/blob/d5e7498bcd7f9c4861a26e587ad2d4e7842035be/Cargo.lock), [memory map](https://github.com/numachang/cornix-rmk-custom/blob/d5e7498bcd7f9c4861a26e587ad2d4e7842035be/memory.x) and [build configuration](https://github.com/numachang/cornix-rmk-custom/blob/d5e7498bcd7f9c4861a26e587ad2d4e7842035be/.cargo/config.toml) demonstrate much greater RAM headroom and flip-link. Its keyboard TOML supplies static peer address fields and host `use_2m_phy = false`, with board-specific DC/DC enabled. The generated macro owns effective clock/address/controller choices; configuration strings alone are not a complete runtime trace. Do not copy DC/DC without fitted-inductor evidence or those older address fields onto modern RMK.

The NocFree ZMK [left defconfig](https://github.com/NocFreeKB/NocFree-and-zmk/blob/8bc5f6fe4531cadc62dc39aa92750fba90e009c4/boards/nocfree/nocfree_and/nocfree_and_left_nrf52833_zmk_defconfig) explicitly calibrates RC rather than assuming an unverified LF crystal and enables MPU/stack protection. It uses CDC only for bootloader recovery, not an enabled USB logging backend. Its selected experimental connection option disables 2M. ZMK's pinned [BLE Kconfig](https://github.com/zmkfirmware/zmk/blob/6e2ef41e022d555b10f116e395832913f71717b3/app/Kconfig#L160-L201) selects Secure Connections-only and treats passkey entry as a separate option; the examined board defconfigs do not enable that option. Generated final configuration would still be needed to prove effective defaults.

Cornix [issue 1](https://github.com/numachang/cornix-rmk-custom/issues/1) provides a specific source-derived correction for charge-only USB falsely taking output away from BLE, later maintainer hardware-confirmed. Our pinned [USB suspend handler](https://github.com/rmk-rs/rmk/blob/9607aedf343b17dd6b27307583ae80c4f728fbbd/rmk/src/usb/mod.rs#L711-L740) already preserves the distinction between never-configured USB and live suspended USB. This issue concerns report routing after connectivity, not accepted pairing followed by a security failure, and does not justify another speculative USB-state patch.

## Ranked, bounded next evidence

1. **Separate logger startup from pairing.** Offline compare the exact working and logger artifacts: linked RAM/static extent versus available stack, logger/CDC descriptor allocations, resolved log/security features and preserved startup/USB fixes. A cross-build passing does not prove dynamic stack safety. Reuse retained-image recovery gates; no new security changes while the observation channel cannot start.
2. **Correlate runtime liveness with one security attempt once observation works.** Existing RMK logs contain PairingFailed, encryption and disconnect reasons. A live USB stream showing a normal security error differentiates a rejected procedure from application halt. Loss of USB alone cannot identify which task or exception failed. Warn logging captures pairing errors but omits Info-level encryption/disconnect messages; determine whether that tradeoff is sufficient before changing logging again.
3. **Locate the security failure on the wire or in existing framework events.** A correlated SMP/HCI capture can distinguish invalid public key, DHKey mismatch, host cancellation, encryption/controller failure or supervision timeout. Status `708` remains unmapped. Do not infer Trouble's 30-second SMP timeout from the 2.091-second host interval.
4. **Only then test the matching hypothesis.** Old Just Works and RPA fixes are already in the pin, optimized ECDH is enabled, and one-central/one-peripheral capacity matches the same-chip example. Unsupported LF crystal selection, global feature toggles, arbitrary bond clearing, whole-stack replacement and ESB migration would change several independent boundaries without resolving this evidence gap.

No peer source establishes no-loss or zero-lag behavior for our keyboard. Split disconnect/release recovery, simultaneous input and measured wake latency remain acceptance work after host pairing and the observation channel are stable.
