# Community backlight patterns

Source review, 2026-10-02. No implementation or hardware operation. These examples demonstrate software patterns, not NocFree pin assignments, electrical compatibility, latency or hardware acceptance.

## What the examples provide

| Example, immutable revision | Controls and output | Persistence | Split behavior |
|---|---|---|---|
| Voyager `69527d634003f7e88fe4d7bfa84431ac5d8e4309` | An `ActionEvent` subscriber handles pressed `Action::Light` RGB actions. `RgbVai`/`RgbVad` saturate brightness; other actions change effects, palette and speed. Board driver writes IS31FL3731 PWM registers over I²C. | Reviewed brightness/palette/effect/speed are local task variables initialized at startup. Keymap storage is separate; no lighting save/load path was found in this task. | One controller directly drives both LED chips at I²C addresses 0x74/0x77. This is not BLE split lighting synchronization. |
| Cornix Prospector `102b4af0abdcfab6f4b453f249f874c7bb5d7862` | A small processor handles pressed `Action::User(10/11)` from Vial custom `BL Up`/`BL Down` keys. It drives the **dongle LCD**, with 16 saturating, roughly geometric levels including off, using 1 kHz nRF PWM. | Explicitly not persisted: always starts at maximum. | Keyboard key actions can control one central/dongle LCD. No synchronized per-half keyboard-backlight state is supplied by this module. |

Voyager pins RMK crate 0.9.0 and enables optional `rmk-palettefx`; its event task polls rendering and shares the scanning I²C mutex. This is inspiration for consuming framework actions, not proof its blocking LED writes meet our input-latency requirements. See [action task](https://github.com/jpds/rmk-zsa-voyager/blob/69527d634003f7e88fe4d7bfa84431ac5d8e4309/src/main.rs#L259-L415), [two-chip driver](https://github.com/jpds/rmk-zsa-voyager/blob/69527d634003f7e88fe4d7bfa84431ac5d8e4309/src/is31fl3731.rs#L300-L370), and [dependencies](https://github.com/jpds/rmk-zsa-voyager/blob/69527d634003f7e88fe4d7bfa84431ac5d8e4309/Cargo.toml#L8-L35).

Cornix pins RMK `65df15775026bad1189139613ee3d338139bec3d`. Its useful precaution is to keep `ActionEvent` processing short and separate from LCD drawing: the display polls an atomic brightness/revision snapshot rather than subscribing to every key action. The source explains event-channel backpressure, but its statement that the display can never delay input is an author claim, not measured NocFree evidence. See [backlight processor and levels](https://github.com/cffnpwr/cornix-prospector-rmk/blob/102b4af0abdcfab6f4b453f249f874c7bb5d7862/src/backlight.rs), [custom key definitions](https://github.com/cffnpwr/cornix-prospector-rmk/blob/102b4af0abdcfab6f4b453f249f874c7bb5d7862/vial.json), [dependency](https://github.com/cffnpwr/cornix-prospector-rmk/blob/102b4af0abdcfab6f4b453f249f874c7bb5d7862/Cargo.toml#L35-L41), and [documented reset-on-boot policy](https://github.com/cffnpwr/cornix-prospector-rmk/blob/102b4af0abdcfab6f4b453f249f874c7bb5d7862/README.md#L73-L80).

## Vial keys are distinct from its lighting GUI

Both reviewed example `vial.json` files omit a `lighting` capability. Cornix exposes custom keys; Voyager handles standard light actions assigned in a keymap. Neither fact establishes a functioning Vial Lighting tab or VialRGB protocol implementation. Official Vial documentation requires matching firmware support plus a `lighting` declaration such as `qmk_backlight` or `vialrgb`; its RGB GUI is based on QMK's RGB Matrix/VialRGB protocol. Adding a JSON declaration alone does not implement it. [Pinned Vial lighting documentation](https://github.com/vial-kb/vial-kb.github.io/blob/4c996015fd64b8e8120ce66251e0634d8dc72dbd/docs/docs/lighting.md), [Voyager definition](https://github.com/jpds/rmk-zsa-voyager/blob/69527d634003f7e88fe4d7bfa84431ac5d8e4309/vial.json).

## What our pinned RMK provides

At `9607aedf343b17dd6b27307583ae80c4f728fbbd`, RMK publishes each resolved `ActionEvent` asynchronously, including presses and releases. Its built-in `Action::Light` branch currently warns that light control is unsupported. `light.rs` handles host keyboard indicator reports, which is not a PWM backlight engine. The reviewed `SplitMessage` enum carries indicators, layers, sleep and connection state, but no backlight brightness state. Existing generic storage does not make an arbitrary board lighting variable persistent. [Action publication and branch](https://github.com/rmk-rs/rmk/blob/9607aedf343b17dd6b27307583ae80c4f728fbbd/rmk/src/keyboard.rs#L1203-L1305), [indicator reader](https://github.com/rmk-rs/rmk/blob/9607aedf343b17dd6b27307583ae80c4f728fbbd/rmk/src/light.rs), [split messages](https://github.com/rmk-rs/rmk/blob/9607aedf343b17dd6b27307583ae80c4f728fbbd/rmk/src/split/mod.rs#L37-L78).

ZMK provides the fuller framework pattern: its backlight behavior has global locality across connected split parts; its backlight module stores enabled/brightness state through Zephyr settings with delayed saves. This means synchronized behavior invocation, not necessarily replaying brightness to a peripheral that was disconnected when a change occurred. Do not infer reconnect replay without tracing that separately. [Pinned global behavior](https://github.com/zmkfirmware/zmk/blob/6e2ef41e022d555b10f116e395832913f71717b3/app/src/behaviors/behavior_backlight.c#L160-L167), [state/save implementation](https://github.com/zmkfirmware/zmk/blob/6e2ef41e022d555b10f116e395832913f71717b3/app/src/backlight.c#L37-L111), [documented behavior](https://github.com/zmkfirmware/zmk/blob/6e2ef41e022d555b10f116e395832913f71717b3/docs/docs/keymaps/behaviors/backlight.md).

## Recommendation within this repository's rules

Keep key resolution, lighting state, delayed persistence and split propagation framework-owned. A small upstream RMK lighting service consuming existing light actions, with a board PWM output adapter, is the conventional extension suggested by these examples. Both-half state should have one authority and an explicit reconnect snapshot; repeated deltas alone are insufficient when a half misses a change. Keep the event handler bounded; rendering/animations and flash writes should run independently.

Our AGENTS restricts custom code to the scanner seam or image-safety tools. A board-local backlight processor copied from these repositories would be a new board-plugin exception, rather than compliance with that rule. Prefer a reviewed upstream/framework extension. If choosing a local processor first, explicitly agree that narrow policy exception before implementation; do not hide brightness behavior inside the scanner. No permission is needed for this source-only research.

The [NocFree community pin map](https://github.com/NocFreeKB/NocFree-and-zmk) identifies P0.20 as the backlight output on both halves; our [earlier board investigation](backlight-path.md) records the factory output behavior. Physical polarity, enable circuitry, allowable current and shared peripheral resources still need board-specific verification. These other keyboard repositories do not establish them.

Persistence changes also need a migration plan: our receiver-support trial demonstrated that changing RMK's feature/schema hash resets stored bonds. Do not promise pairing preservation when adding storage or changing features without checking that compatibility first. No host test or cross-build here is hardware validation.
