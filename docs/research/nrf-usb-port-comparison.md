# nRF52833 USB port comparison

Research date: 2026-10-01. This is source research, not hardware validation. No firmware, bootloader, UICR or dock changes were made for this comparison.

## Scope and exact dependencies

The local firmware selects **nRF52833**, not nRF52840: `firmware/Cargo.toml` enables `embassy-nrf/nrf52833`, `nrf-sdc/nrf52833`, and `nrf-mpsl/nrf52833`. Its lockfile resolves Embassy nRF **0.11.0** and USB **0.6.0**. Published crate source identifies revisions [3861d3088da30d40c777dc05d282352e68ec5511](https://github.com/embassy-rs/embassy/tree/3861d3088da30d40c777dc05d282352e68ec5511/embassy-nrf) and [50c6aac5b9b3b0af18f5a7d61725cc8e4d1f7acb](https://github.com/embassy-rs/embassy/tree/50c6aac5b9b3b0af18f5a7d61725cc8e4d1f7acb/embassy-usb). Do not substitute an older Embassy release when interpreting this trial.

The diagnostic explicitly selects `HfclkSource::ExternalXtal`, binds USBD and CLOCK_POWER, constructs HardwareVbusDetect, and runs the ordinary Embassy USB framework. It does **not initialize MPSL or SDC**. Merely depending on those crates does not run their initialization. Its 64-byte control buffer, CDC class and composite IAD settings must be compared against other CDC configurations, rather than HID key behavior.

## What the reset-positive result really narrows

The new device observation is a positive return through `Handler::reset()` to the existing serial bootloader. Prior observations reached initialization/build/enabled callbacks but not the configured callback. See [reset candidate](usb-reset-candidate.md) and [callback candidates](usb-callback-candidates.md) for the bounded observations and exact images.

Importantly, **reset-positive does not prove the USBD interrupt reached the application's handler**. In the pinned [nRF driver](https://github.com/embassy-rs/embassy/blob/3861d3088da30d40c777dc05d282352e68ec5511/embassy-nrf/src/usb/mod.rs#L232-L256), `Bus::poll` reads the latched USBRESET register directly and returns Reset. The [interrupt handler](https://github.com/embassy-rs/embassy/blob/3861d3088da30d40c777dc05d282352e68ec5511/embassy-nrf/src/usb/mod.rs#L35-L55) supplies wakeups, not the only possible way to read that event. A latched event at an ordinary executor poll can reach the callback without proving correct vector delivery for subsequent EP0 events.

The configured-positive callback would require substantially more progress through control enumeration. Product missing/interface classes missing are host observations, not a trace of which SETUP request failed. A VID/PID observation may indicate a device descriptor reached the host, but does not prove every descriptor, string or configuration completed.

## Ranked, falsifiable hypotheses

1. **EP0 progress / interrupt forwarding after reset.** Highest priority because reset can be register-polled while [SETUP handling](https://github.com/embassy-rs/embassy/blob/3861d3088da30d40c777dc05d282352e68ec5511/embassy-nrf/src/usb/mod.rs#L611-L704) waits on EP0 wakeups after becoming Pending. Audit the exact MBR forwarding and installed vector table, then inspect whether the application's USBD handler is reached, before assuming reset-positive eliminated interrupts. Falsifier: verified USBD handler delivery plus successful descriptor/control completions moves the boundary later. The existing recovery marker route must remain intact during any future observation.
2. **Control-transfer data stage / EasyDMA stalls.** The pinned driver's [write_dma](https://github.com/embassy-rs/embassy/blob/3861d3088da30d40c777dc05d282352e68ec5511/embassy-nrf/src/usb/mod.rs#L549-L574) copies flash data to RAM when needed, then synchronously waits for ENDEPIN; an event that never arrives stalls the executor. This cannot be distinguished from an EP0 wait by host identity alone. Falsifier: demonstrate completed descriptor IN DMA and status handling; then investigate a later SETUP request instead. Do not implement a replacement USB driver on speculation.
3. **Bootloader warm-state mismatch.** Plausible when behavior differs between DFU launch and genuine reset; weakened here by the battery-first sequence. A bootloader jump is not necessarily a chip reset. Audit current driver enable/disable, CLOCK/POWER event state and MBR handoff against the exact bootloader source. The diagnostic's ExternalXtal path explicitly clears HFCLKSTARTED before starting HFXO in [HAL initialization](https://github.com/embassy-rs/embassy/blob/3861d3088da30d40c777dc05d282352e68ec5511/embassy-nrf/src/lib.rs#L1161-L1181), so copying an unrelated stale-HFCLK workaround is not justified. Falsifier: equivalent clock/power/interrupt state at the relevant boundary under both launch routes.
4. **Descriptor or host-specific rejection.** Lower priority: basic settings resemble the standard CDC example and a right diagnostic already works, but a failed string/configuration request remains possible. Falsifier: host control trace shows correct descriptor bytes and successful SET_CONFIGURATION; an alternate host/direct USB connection isolates dock/host behavior. Increasing all buffers or changing VID/PID is not a diagnosis.

These are priorities for discriminating evidence, not identified causes. Root's separate MBR/vector audit should refine hypothesis 1 before another device trial.

## Upstream issues and fixes: relevant versus misleading

- [Embassy issue 4105](https://github.com/embassy-rs/embassy/issues/4105) reports LED tasks working but no CDC after Adafruit serial DFU on an **nRF52840**. It has no established resolution in the issue body/comments returned by this inspection. It supports investigating bootloader handoff; it does not provide a proven patch.
- [nRF SDC issue 103](https://github.com/alexmoon/nrf-sdc/issues/103) reports MPSL initialization failure with an app at `0x1000` and resident MBR on an **nRF52840**. A [subsequent comment](https://github.com/alexmoon/nrf-sdc/issues/103#issuecomment-5910654118) reports POWER/HFCLK state left by an Adafruit bootloader at a **different application address, `0x26000`**, with a reset workaround. The [author's correction](https://github.com/alexmoon/nrf-sdc/issues/103#issuecomment-5912487157) explicitly says the original no-USB example differs. These are author reports, not verified NocFree results. Our USB-only diagnostic never initializes MPSL; do not use this issue to claim the present failure is an MPSL bug. It becomes an integration risk when full RMK radio starts.
- [Embassy PR 6688](https://github.com/embassy-rs/embassy/pull/6688), merged as [652e02421ed649b7ca6450c695287a90776aec7b](https://github.com/embassy-rs/embassy/commit/652e02421ed649b7ca6450c695287a90776aec7b), removes an extra OUT re-arm after DMA and adds erratum 199 handling. The hardware report concerns sustained CDC **OUT data loss on nRF52840**, not enumeration. The erratum workaround is explicitly `cfg(nrf52840)`, so it does not run for our chip. The shared OUT fix deserves evaluation before promising lossless transfers, but no evidence here identifies it as this EP0-enumeration cause. nRF52833 cross-build in that PR is software validation only.
- [Embassy HID issue 6891](https://github.com/embassy-rs/embassy/issues/6891) concerns resetting Boot/Report protocol state after a later bus reset. It cannot explain failure of this CDC diagnostic before configuration. Likewise [bInterval issue 6596](https://github.com/embassy-rs/embassy/issues/6596) concerns high-speed interval encoding; this full-speed nRF52 enumeration investigation is a different boundary.

## Recommended next work

Complete the offline MBR/vector/interrupt audit first. Prefer a single source-backed correction if that finds a concrete mismatch. If it remains ambiguous, use one bounded observation that distinguishes EP0 interrupt delivery from DMA/control-transfer progress, preserving the independently proven recovery route. Do not replace the bootloader, weaken address guards, switch frameworks, or blanket-upgrade Embassy to hunt this failure. Independently evaluate the upstream OUT-data fix for eventual transport acceptance after enumeration works.
