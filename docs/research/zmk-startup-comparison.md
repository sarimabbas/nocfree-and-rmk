# NocFree ZMK startup comparison

Read-only primary-source research on 2026-10-01. No firmware changes, device operations, or new installation authorization. The purpose is to shorten the path to left-side RMK USB typing.

## Exact comparison inputs

Community repository HEAD inspected: [`8bc5f6fe4531cadc62dc39aa92750fba90e009c4`](https://github.com/NocFreeKB/NocFree-and-zmk/tree/8bc5f6fe4531cadc62dc39aa92750fba90e009c4). Its [manifest](https://github.com/NocFreeKB/NocFree-and-zmk/blob/8bc5f6fe4531cadc62dc39aa92750fba90e009c4/config/west.yml) pins ZMK [`6e2ef41e022d555b10f116e395832913f71717b3`](https://github.com/zmkfirmware/zmk/tree/6e2ef41e022d555b10f116e395832913f71717b3). ZMK's [manifest](https://github.com/zmkfirmware/zmk/blob/6e2ef41e022d555b10f116e395832913f71717b3/app/west.yml) imports Zephyr `v4.1.0+zmk-fixes`, resolved during this research to [`10ba6d0cb38bc3d258775d27982f707599320085`](https://github.com/zmkfirmware/zephyr/tree/10ba6d0cb38bc3d258775d27982f707599320085). The latter is a tag reference in the manifest; record the resolved commit when reproducing rather than assuming the name is immutable.

Our comparison is `firmware/src/bin/recovery-probe.rs`, not the full RMK central. It explicitly selects external HFXO, retains the default internal-RC LFCLK, uses Embassy HardwareVbusDetect and USBD interrupt bindings, and constructs a standard composite CDC device. Its migration image is linked at `0x1000`; current USB-reset evidence is recorded separately in [usb-reset-candidate.md](usb-reset-candidate.md). Framework sources for this exact probe are pinned in [usb-startup-boundaries.md](usb-startup-boundaries.md).

## Evidence strength

The community [limitations/hardware record](https://github.com/NocFreeKB/NocFree-and-zmk/blob/8bc5f6fe4531cadc62dc39aa92750fba90e009c4/docs/limitations.md) reports one ANSI unit on macOS: bootloader S140 7.3.0, left 37-key check over USB/BLE, assembled split operation, and 1200-baud recovery on both halves. These are the community maintainer's reported observations, not measurements reproduced on our board. It explicitly does not claim factory rollback or power-cycle reconnection testing, Windows/Linux validation, battery life, measured latency or other hardware revisions. The same document leaves battery, backlight, dongle, mode-switch handling and deep sleep absent. This is useful proof of a conventional `0x27000` ZMK application, not a shortcut to a complete modern RMK firmware.

## Focused next work

1. Compare optimized working factory-layout USB probe and lower-layout probe descriptors, EP0 allocation, reset/setup/EP0DATADONE handling and callback ordering using the exact Embassy revision. Avoid another full migration or factory restore simply to restate the current result.
2. Inspect USB setup/control source and known upstream fixes before preparing another candidate. If instrumentation is needed, select a framework-supported request boundary that separates “host reset arrived” from “first descriptor request was handled”; do not introduce a custom USB stack or declare an interrupt-mask fault from absence alone.
3. Resume full RMK left typing after the USB-only control enumerates. Community pin/scanner evidence is valuable at that later seam; it does not explain a pre-scanner control-endpoint failure.

No new source patch or firmware transfer is justified by this comparison alone. The strongest useful conclusion is that the community port contains no special board USB trick, while its preserved-S140 boot path differs from the layout presently under investigation.

## Interrupt-state comparison: narrower than a cleanup recipe

The inspected upstream Adafruit [bootloader_app_start](https://github.com/adafruit/Adafruit_nRF52_Bootloader/blob/0147d71e73b9a2c217f56dbc9877d07bb45d6467/lib/sdk11/components/libraries/bootloader_dfu/bootloader.c#L357-L401) clears NVIC enable/pending banks, selects S140 forwarding or MBR IRQ forwarding according to SoftDevice presence, then branches through [bootloader_util_reset](https://github.com/adafruit/Adafruit_nRF52_Bootloader/blob/0147d71e73b9a2c217f56dbc9877d07bb45d6467/lib/sdk11/components/libraries/bootloader_dfu/bootloader_util.c). Its GCC handoff writes MSP and branches to Reset, including handler-mode exit logic, but does not explicitly clear PRIMASK/BASEPRI/CONTROL. This is upstream base source, not the complete vendor binary.

Zephyr's ARMv7-M reset path writes a known BASEPRI locking threshold. Its [IRQ init](https://github.com/zmkfirmware/zephyr/blob/10ba6d0cb38bc3d258775d27982f707599320085/arch/arm/core/cortex_m/irq_init.c) resets individual IRQ priorities, and [context switching](https://github.com/zmkfirmware/zephyr/blob/10ba6d0cb38bc3d258775d27982f707599320085/arch/arm/core/cortex_m/swap_helper.S#L198-L261) restores the incoming thread BASEPRI. The `cpsie i` visible in that function is in the ARMv6-M/ARMv8-M-baseline branch, not the nRF52833 ARMv7-M branch. Therefore do not claim this community port universally clears inherited PRIMASK simply because Zephyr has interrupt-enable instructions somewhere in its source. Optional early architecture cleanup still requires generated configuration evidence.

Our observed `Handler::reset` likewise does not by itself prove global interrupt masks are clean: Embassy [Bus::poll](https://github.com/embassy-rs/embassy/blob/3861d3088da30d40c777dc05d282352e68ec5511/embassy-nrf/src/usb/mod.rs#L232-L251) reads the USBRESET register directly and can return an already-present event during polling. Interrupt delivery remains a measurement question. Conversely, this source does not demonstrate a bad mask; a missing configuration callback is not sufficient evidence to add blanket core-state normalization. If warm-handoff mask behavior is pursued, first capture PRIMASK/BASEPRI/CONTROL and relevant IRQ priorities at an observable boundary, or perform a tightly scoped independently reviewed differential candidate; keep the existing hardware recovery route and exact image guard.
