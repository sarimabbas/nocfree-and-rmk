# Companion local firmware release

`python3 scripts/package_companion_release.py` produces the fixed local release in ignored `dist/companion-firmware`. `--check` validates without generating files. The script reads private review and installed UF2 readback evidence for each role, binds exact candidate hashes, and reruns the address/vector/family guard. It neither queries devices nor writes firmware. Factory firmware is never packaged.

This local release contains the verified ANSI layout with Mac key behavior; it is not presented as a separate tested Windows/Linux keymap release. The package contains a schema-1 manifest plus an exact UF2/BIN pair for left, right and dongle. The current local package is `0.1.0-local.2` / `nocfree-98a65111d4f3fae0`. LEFT and dongle use the reviewed pairing-protocol checkpoint `94f83b59617b9323bbc484d2440b487848291422` with RMK `0afc58c9db423313faa0c47021fc7957f4416a11`; RIGHT uses lighting checkpoint `1acd812a82e0ae3e99a1d498af52c0e1f37fa916` with RMK `33214e095a86e21bac6184ab9e4d3565ba72a849`. Each role binds its exact installed UF2/BIN pair, not the newest unverified build. LEFT and dongle now include the NCPR Check pairing protocol; RIGHT remains the verified split peripheral. The two half calibrations are provisional 150/100 voltage estimates, not a validated battery capacity model. The dongle retains S140; the halves use reclaimed application space. Storage schema changes can require re-pairing when installing from a different revision.

Companion loads `Contents/Resources/Firmware` in its app bundle. A debug build can use the generated dist directory. The code pins the exact manifest hash, denies unknown fields, bounds file sizes, accepts only plain filenames, binds each role to its exact UF2/BIN hashes and reruns the Rust image guard. An edited manifest or a structurally valid image from another role is rejected. Public imports do not become trusted releases.

These images have hash-bound role-specific passed operator reviews, complete stored installed readbacks, exact application and erased padding, and unchanged flash outside the application through the storage boundary. The package reruns those comparisons against each original full backup, including the dongle S140 prefix. All three stored readbacks report changed settings after the RMK revision change; the manifest records `storage_preserved: false` and does not label a reset as preservation.

Recovery provenance is retained evidence, not a fabricated observation on this image. LEFT retains its calibration checkpoint's observed Companion runtime recovery, RIGHT its reviewed runtime-recovery trial, and the dongle its closed-case runtime recovery observation. Source comparison from the proven RMK revisions to these pins found no changes to `usb/dfu.rs`, `usb/dfu_detach.rs`, `usb/runtime_dfu_scope.rs`, or the watchdog implementation. The board `watchdog_recovery.rs` is also unchanged. The USB module's only relevant difference is USB-power awake bookkeeping in its enabled callback, not DFU handling. The manifest explicitly says `recovery_evidence: retained_role_specific_route_unchanged` and `current_image_runtime_recovery: false`: current-image runtime Companion recovery acceptance has not been separately recorded. Exact recovery readbacks establish byte identity and drive availability; they do not establish how the drive was entered. A deliberate dongle crash/recovery test remains unperformed.

Package validation neither touches devices nor authorizes installation. The installer still requires fresh device-specific recovery, same-port correlation and full backup, then one-shot copying and exact verification.

USB names indicate a role, never a firmware version. Whether a board already has the release must be determined from exact recovery readback, with a saved checkpoint used only as a record of that observation. Updating the allowlist requires another reviewed, role-specific package and a new release ID.
