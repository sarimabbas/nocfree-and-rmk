# Next milestone: validate the lower application layout

Research 2026-10-01. No device operations, serial opens or writes were performed by this review. Recommendation: prepare a left-only USB recovery diagnostic linked at `0x1000`, then seek a separate, concrete migration-trial approval. Keep the installed MBR and Adafruit bootloader. Validate the new boot address and full factory restoration before introducing the full RMK central's radio, storage and battery tasks.

## Current hardware evidence and what transfers

The owner/root have now verified the left's S140-preserving diagnostic at `0x27000`: USB identity/greeting, update entry, exact readback, WIRED USB-unplug/replug recovery without key input, Bluetooth battery-first application startup, exact factory restoration and diagnostic reinstallation. Final startup and the owner's requested left letters/numbers, Shift, Space and Tab checks passed. Those observations establish this unit's physical operating sequence and the existing bootloader's marker convention at `0x27200`. They do not prove every key/release, transport reliability or wake latency.

The same enclosure-closed switch/cable sequence is a justified starting hypothesis for migration. Its physical mechanism need not change when application origin changes, but the bootloader must newly select `0x1000`, find the marker at `0x1200`, validate the new image, forward interrupts without resident S140 and launch it. Each of those remains a migration-specific hardware gate. Existing factory restoration rewrote only the application slot, so restoration of overwritten S140 remains untested. No left migration or receiver write was authorized by the earlier diagnostic trial.

## Exact upstream evidence

The installed build reports base commit `0147d71e73b9a2c217f56dbc9877d07bb45d6467`. This review fetched the files at that exact commit. The version string identifies a base; it does not establish equivalence to the vendor bootloader binary.

- [dfu_types.h](https://github.com/adafruit/Adafruit_nRF52_Bootloader/blob/0147d71e73b9a2c217f56dbc9877d07bb45d6467/lib/sdk11/components/libraries/bootloader_dfu/dfu_types.h): `is_sd_existed()` checks S140 magic `0x51b1e5db` at `0x3004`. `CODE_REGION_1_START`/`DFU_BANK_0_REGION_START` select the SoftDevice-reported size while that magic exists, otherwise MBR end `0x1000`. Merely relinking or writing a vector at `0x1000` cannot change the selection while the old magic survives.
- [main.c](https://github.com/adafruit/Adafruit_nRF52_Bootloader/blob/0147d71e73b9a2c217f56dbc9877d07bb45d6467/src/main.c): the recovery word is read at the dynamically selected application base plus `0x200`. USB DFU uses the existing three-second recovery-first convention. Starting an application conditionally initializes/disables S140 only when detected. GPREGRET skip and retained-RAM fast-start paths are relevant exceptions, so validate an actual physical startup rather than only a post-update launch.
- [bootloader.c](https://github.com/adafruit/Adafruit_nRF52_Bootloader/blob/0147d71e73b9a2c217f56dbc9877d07bb45d6467/lib/sdk11/components/libraries/bootloader_dfu/bootloader.c): application validity uses the selected base and stored bank-valid/CRC metadata. With no S140, startup requests MBR IRQ forwarding to `0x1000`; on forwarding failure it writes the fallback address to the first SRAM word. Preserve the current `0x20008000` application RAM floor for this milestone. Application-completion metadata writes bootloader settings; retaining bootloader code does not mean its settings page stays byte-identical.
- [ghostfat.c](https://github.com/adafruit/Adafruit_nRF52_Bootloader/blob/0147d71e73b9a2c217f56dbc9877d07bb45d6467/src/usb/uf2/ghostfat.c): ordinary generic or board-specific application-family UF2 blocks write their explicit target addresses throughout user flash, treating S140 as part of that application image. MBR addresses are skipped upstream; our guard must reject them instead. The distinct bootloader-family path permits other sensitive writes and must be rejected. The readback uses board-specific application family, not generic chip family.
- [msc_uf2.c](https://github.com/adafruit/Adafruit_nRF52_Bootloader/blob/0147d71e73b9a2c217f56dbc9877d07bb45d6467/src/usb/msc_uf2.c): completing every advertised UF2 block submits an application-complete event with zero-initialized CRC/size. Combined with `bootloader.c`, this marks the image valid without a stored image CRC check. Host structural guards and exact readback are essential; MSC completion alone is not image integrity evidence.
- [dfu_single_bank.c](https://github.com/adafruit/Adafruit_nRF52_Bootloader/blob/0147d71e73b9a2c217f56dbc9877d07bb45d6467/lib/sdk11/components/libraries/bootloader_dfu/dfu_single_bank.c): ordinary application serial DFU uses the selected application base for erase and data writes. It initially sees S140 and therefore starts at `0x27000`. Its raw BIN does not carry UF2 target addresses. Existing serial ZIP guards also require S140 FWID `0x0123`. Do not reuse that route or its metadata for the first migration or a restore containing S140; dynamic base changes during a differently constructed serial transfer introduce additional hazards.

## Smallest candidate

Prepare a separate explicit migration diagnostic using the existing USB-only recovery probe implementation: external HFXO, CDC greeting and the existing bootloader-entry action. It should identify itself as left/migration with a distinct development product/version, reserve `0x87eeb07c` at `0x1200`, use `0x1000..0x65000` flash and the existing application RAM floor. Start no scanner, BLE/MPSL runtime, battery ADC, lights or storage tasks. Reuse the tested code rather than writing another updater or boot shim; retain strict factory-only guards on the existing input diagnostic.

The candidate must contain contiguous addressed data starting at `0x1000` and covering the entire word at `0x3004`, whose final value must differ from S140 magic. A normal USB diagnostic should be larger than this minimum, but check the actual linked bytes. The marker must precede text without overlapping vectors. Record ELF-to-BIN equality, vector SP/PC, exact end, every touched/erased page and package hashes. Pad only through its final touched page; compare the remaining readable flash against the pre-trial image. Do not clear all old S140/application flash just to make it tidy.

Use an ordinary generic nRF52833 application-family UF2 (`0x621e937a`) for this addressed transfer. The migration guard must be separate from the factory-preserving policy: enforce exact origin `0x1000`, exclusive limit `0x65000`, unique contiguous aligned 256-byte blocks, count/magics/flags, valid application RAM SP, Thumb PC within executable BIN coverage, marker at `0x1200`, and absent S140 magic at `0x3004`. Reject bootloader family, UICR and MBR blocks rather than relying on bootloader filtering. Independent review and all supported-role builds precede any device trial. Guard tests are software evidence only.

## Restore gate

Retain and independently validate the exact left factory `CURRENT.UF2`, SHA-256 `88cb768f452682cb12025f2296ee151442349079405a7a11f454f752153e4100`. Its 1,728 blocks cover exactly `0x1000..0x6d000` with family `0x239a0029`. This is the restore image for S140 plus factory application/settings, not the previous `0x27000..0x65000` restore ZIP and not a full-chip backup.

Use a distinct restore validator bound to this role and exact hash: require complete block numbering/address coverage, custom application family, S140 magic/size/FWID/version and valid factory vectors at `0x27000`. Disallow additional addresses, bootloader-family blocks and changes to the saved payload. Its expected S140 magic and absent development marker are intentional, so it must not be passed through candidate migration policy. Reusing the original container avoids needless regeneration. Confirm the freshly connected device's bootloader identity and the current diagnostic bytes before transfer; serial/USB IDs alone are insufficient role identity.

After restore, require complete readable `CURRENT.UF2` equality to the original backup and factory enumeration. That verifies all readable bytes, including S140 and factory settings. It cannot verify excluded MBR, filesystem, bootloader code or UICR. Candidate and restore bounds protect those excluded regions; bootloader completion metadata is the expected settings exception.

## Proposed authorized hardware sequence

1. Prepare/review the candidate, restore guard and exact packages; keep both halves' known-good artifacts. Present exact role, addresses, hashes and remaining risks for **new left migration approval**. Existing trial approval does not cover overwriting S140.
2. Identify the left bootloader after its already-tested independent WIRED USB-first sequence. Recheck INFO and full current readback before any migration transfer. Keep the right diagnostic and dongle untouched.
3. Transfer only the guarded addressed migration UF2. Observe USB identity/greeting if it launches, then return to MSC if possible. Require all candidate bytes and expected touched-page tails to match; compare retained readable addresses. INFO should report no SoftDevice while retaining its bootloader identity fields; identical INFO text is no longer the correct expectation.
4. Test physical WIRED USB-first recovery without application commands; verify readback again. Test the known Bluetooth battery-first sequence and USB greeting independently. Do not count a software reboot as independent recovery.
5. Restore the complete guarded factory UF2 through MSC and verify full backup equality and factory enumeration. If this fails, stop; do not progress to full RMK or another role.
6. Only after these gates pass, choose whether to reinstall the migration diagnostic or return to the current factory-layout input diagnostic within the approved trial scope. A full RMK central is the next separate milestone, with its usual split/disconnect/release/simultaneous-input/wake acceptance.

## Remaining risk

The verified physical path reduces application-code dependence but does not establish the vendor's lower-layout branch, complete S140 restoration, or interrupted-update recovery. A partial addressed copy can erase the marker or leave contradictory S140 metadata before completion; bank validity and dynamically selected vectors can then disagree. Do not deliberately interrupt power to test that with no independently accessible reset/probe. MSC/host write ordering must not be advertised as atomic or automatically rolled back. A failed lower-layout bootloader path could require opening the enclosure or a probe despite retaining its code. This is the specific additional risk to explain before asking for migration approval.
