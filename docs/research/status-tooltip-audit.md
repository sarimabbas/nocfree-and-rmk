# Status tooltip audit

Audited 2026-10-04. No app or firmware behavior changed in this audit.
All explicit app tooltips are generated by `desktop/src/status_strip.rs`;
the same text is used as the accessibility label.

## Three independent facts

- **Selected mode:** physical switch selection: Wired, Bluetooth or Dongle.
- **Typing route:** the verified connection carrying input to the host. A USB
  cable does not establish this when another mode is selected.
- **USB power:** whether the half has USB power. This does not establish active
  charging, an input route, or the other half's power state.

Recovery is a separate per-device state. A recovery USB interface is not a
typing connection. The right's wireless connection is to the left; the dongle's
USB attachment is to the host. These links must not share one generic connected
boolean.

## Current tooltip coverage

`M` below is the reported or inferred mode, otherwise "Mode unavailable".
`B` is the visible cached battery percentage, otherwise "Battery unavailable".
Recovery appends "Recovery mode" to every applicable row.

| Peripheral / condition | Current text after device name | Finding |
| --- | --- | --- |
| Left, Bluetooth without USB | M. Bluetooth connected. B | Redundant when M is Bluetooth; mode may be inferred from this same connection |
| Left, dongle without USB | M. Connected through dongle. B | Same duplication; dongle link is inferred from a battery reply |
| Left, USB in Wired | M. USB connected. B | Does not distinguish USB power from input |
| Left, USB in Bluetooth | Bluetooth mode. USB connected. B | Cable masks any active Bluetooth link in the derived connection |
| Left, USB in Dongle | Dongle mode. USB connected. B | Cable masks any active dongle link in the derived connection |
| Left, disconnected | M. Not connected. Battery unavailable | Mode can remain stale; selected-mode icon can look connected |
| Left, recovery | M. USB connected. B. Recovery mode | Claims a normal connection based on recovery enumeration |
| Right, USB attached | USB connected. B | No split-link state; no distinction between power and typing |
| Right, connected wirelessly | B | Missing "Connected to left" |
| Right, disconnected | Battery unavailable | Missing "Not connected"; unknown battery and disconnection look identical |
| Right, recovery | USB connected. B. Recovery mode | USB wording is ambiguous, but recovery belongs to the correct half |
| Dongle, normal USB attached | USB connected | Host attachment is valid, but says nothing about keyboard-to-dongle link |
| Dongle, absent | Not connected | Valid for the host attachment |
| Dongle, recovery | Not connected. Recovery mode | Normal dongle detection excludes the recovery interface, causing contradictory wording |

Battery values are hidden by `Levels::visible` when the derived peripheral
connection is absent, and retained across temporary reading gaps as requested.
This behavior should remain; the connectivity inputs need correction.

## State-model defects

1. `Observation::derive` selects USB before Bluetooth or dongle solely from USB
   enumeration, including the recovery drive. It cannot identify an active
   typing route in this way.
2. `render` then replaces the connection icon with the selected-mode icon, while
   retaining the connection description. Icon and text can describe different
   facts. Known mode also overrides the disconnected icon.
3. The mode fallback turns a connection inference into a switch-position claim.
   Keep reported switch mode separate from any inferred route.
4. Charging metadata is decoded into `BatteryStatus`, but the UI stores only
   percentages. The charging glyph depends on host USB enumeration, not charging
   telemetry. It can miss a half powered by another charger, and show charging
   when plugged in at full charge. Treat that glyph as USB power under the
   requested visual convention; do not describe it as confirmed charging.
5. Dongle keyboard-link status comes from availability of a relayed battery
   reply. RMK retains snapshots, so a battery value alone is not a fresh link
   proof. Require explicit current link telemetry.
6. Right-link and switch snapshots lack freshness/identity in the rendered
   status. A failed poll preserves them. In particular, changing battery
   producers clears dongle-link/mode but does not generally clear right-link.
   Cached battery is intentional; cached connectivity must not become authority.
7. USB host discovery cannot detect a charge-only cable or a cable connected to
   a separate charger. Firmware power telemetry is needed for those cases;
   lack of host enumeration is not proof that USB power is absent.

## Recommended presentation

Use one tooltip per peripheral, with each fact stated at most once. Combine
mode and connection when they agree; show selected mode separately only when
the link is disconnected, unknown, or actually different. Recovery replaces
normal typing-link language. Do not claim charging without charging telemetry.

| Verified state | Proposed tooltip |
| --- | --- |
| Bluetooth typing, battery | Left. Bluetooth connected. Battery 100% |
| Bluetooth typing, USB powered | Left. Bluetooth connected. USB power connected. Battery 100% |
| Dongle typing, USB powered | Left. Connected through dongle. USB power connected. Battery 100% |
| Wired typing, USB powered | Left. Wired connected. Battery 100% |
| Bluetooth selected, link absent | Left. Bluetooth mode. Not connected |
| Dongle selected, link unknown | Left. Dongle mode. Connection unavailable |
| Recovery, USB powered | Left. Recovery mode. USB power connected. Battery 100% |
| Right split link, battery | Right. Connected to left. Battery 100% |
| Right split link, USB powered | Right. Connected to left. USB power connected. Battery 100% |
| Right disconnected | Right. Not connected |
| Right recovery | Right. Recovery mode. USB power connected. Battery 100% |
| Dongle normal | Dongle. USB connected |
| Dongle recovery | Dongle. Recovery mode. USB connected |
| Dongle absent | Dongle. Not connected |

Omit battery percentages when the peripheral is disconnected; use "Battery
unavailable" only for a connected peripheral without a known value. Recovery
can retain the last known battery while USB-attached. Never manufacture a value.
"Connection unavailable" means evidence is missing; "Not connected" requires
an actual disconnected observation. Wired connection already implies USB, so
it does not need a duplicate USB-power sentence.

## Acceptance matrix for implementation

Test all left modes against USB power present/absent, link connected/disconnected/
unknown and recovery normal/active. Test each right power/link/recovery
combination, and dongle normal/recovery/absent. Add known/unknown/zero battery
and producer replacement, failed polling, app restart and charger-only cases.
Contradictory observations must produce unknown state rather than a fabricated
route. Tests must compare both tooltip and icon semantics from one immutable
derived status; screenshot checks alone cannot establish routing.

Source review covered every tooltip branch and its upstream inputs. No new
tests or live-device changes were necessary for this read-only audit.

Sources: `desktop/src/status_strip.rs`, `desktop/src/device_status.rs`,
`desktop/src/ui.rs`, `desktop/src/battery.rs`, `desktop/src/battery_vial.rs`.
