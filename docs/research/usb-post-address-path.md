# USB progress after SET_ADDRESS dispatch

Researched 2026-10-02. This is source analysis, not a new hardware result or permission to install an image. The owner-assisted addressed trial reached the standard callback and retained its exact image after recovery checks; [the candidate record](usb-addressed-candidate.md#owner-assisted-hardware-result) states its limits. Full RMK USB startup remains unverified.

## Exact control path

The pinned published sources are Embassy USB 0.6.0 at `50c6aac5b9b3b0af18f5a7d61725cc8e4d1f7acb` and Embassy nRF 0.11.0 at `3861d3088da30d40c777dc05d282352e68ec5511`. Source links below use those revisions rather than moving main.

1. `UsbDevice::run` selects bus polling against `ControlPipe::setup`, then dispatches the resulting eight setup bytes. A legal SET_ADDRESS sets software address/state and the pending flag, then calls `Handler::addressed`. The successful diagnostic resets here. [USB run](https://github.com/embassy-rs/embassy/blob/50c6aac5b9b3b0af18f5a7d61725cc8e4d1f7acb/embassy-usb/src/lib.rs#L274-L297), [dispatch](https://github.com/embassy-rs/embassy/blob/50c6aac5b9b3b0af18f5a7d61725cc8e4d1f7acb/embassy-usb/src/lib.rs#L519-L529).
2. With that callback allowed to return, the outer control handler calls `accept_set_address` and clears the pending flag. In the nRF driver this calls `accept`, writes `TASKS_EP0STATUS = 1`, and returns immediately. **There is no asynchronous status-acknowledgement wait at this boundary.** Peripheral address handling is delegated to hardware; a function-return hook would prove the task write, not a completed host acknowledgement. [Outer handler](https://github.com/embassy-rs/embassy/blob/50c6aac5b9b3b0af18f5a7d61725cc8e4d1f7acb/embassy-usb/src/lib.rs#L430-L443), [nRF accept](https://github.com/embassy-rs/embassy/blob/3861d3088da30d40c777dc05d282352e68ec5511/embassy-nrf/src/usb/mod.rs#L713-L727).
3. The next run iteration calls `setup` again: clear SHORTS, enable EP0SETUP interrupt, register EP0_WAKER, read EVENTS_EP0SETUP, and sleep if absent. Once present it clears the event and reads the setup registers. The ISR disables that interrupt source and wakes EP0_WAKER; it leaves event consumption to the future. This next-setup wait is an unresolved progress boundary. [Setup](https://github.com/embassy-rs/embassy/blob/3861d3088da30d40c777dc05d282352e68ec5511/embassy-nrf/src/usb/mod.rs#L611-L644), [ISR](https://github.com/embassy-rs/embassy/blob/3861d3088da30d40c777dc05d282352e68ec5511/embassy-nrf/src/usb/mod.rs#L37-L54).
4. Descriptor control-IN builds response slices, splits them into EP0 packets and awaits each `data_in`. nRF copies flash-backed bytes through stack RAM, launches EasyDMA and synchronously waits for ENDEPIN before returning from `write_dma`. Then `data_in` awaits EP0DATADONE or abort on reset/new setup. Its last-packet shortcut requests EP0STATUS. **This future already self-wakes on every poll** as well as registering EP0_WAKER. Missing interrupt wakes therefore do not explain this particular await in the same way they could explain idle `setup`; a DMA spin can still prevent the executor from progressing. [Response](https://github.com/embassy-rs/embassy/blob/50c6aac5b9b3b0af18f5a7d61725cc8e4d1f7acb/embassy-usb/src/lib.rs#L363-L391), [DMA](https://github.com/embassy-rs/embassy/blob/3861d3088da30d40c777dc05d282352e68ec5511/embassy-nrf/src/usb/mod.rs#L549-L574), [data-in](https://github.com/embassy-rs/embassy/blob/3861d3088da30d40c777dc05d282352e68ec5511/embassy-nrf/src/usb/mod.rs#L679-L711).
5. SET_CONFIGURATION enables endpoints and calls `configured(true)` before acknowledging its own status stage. The earlier failed configured callback leaves steps 2–4 and arrival/dispatch of SET_CONFIGURATION unresolved. It does not demonstrate that this final callback itself is defective. [Configuration dispatch](https://github.com/embassy-rs/embassy/blob/50c6aac5b9b3b0af18f5a7d61725cc8e4d1f7acb/embassy-usb/src/lib.rs#L530-L547).

Positive addressed dispatch can have occurred through a latched setup consumed on a poll; it is not standalone evidence of interrupt delivery. The working scanner's repeated parent-task wakeups remain a confound for bus/idle-setup waits, while the pinned driver's existing data-IN self-wake narrows that hypothesis. Neither statement diagnoses this hardware.

## Concrete specification mismatch: prioritize a minimal framework correction

The Nordic-authored **nRF52833 Product Specification v1.7**, section 6.33.9, printed page 756, explicitly says the peripheral handles SetAddress itself. Software may update its state machine but must not initiate a status stage; USBADDR reports the assigned address after processing. This is the exact chip, not an inference from nRF52840/nRF5340. The official documentation HTML was too large for the web reader and official PDF fetch failed; the same Nordic-authored document was downloaded transiently in memory from [ANU's mirror](https://comp.anu.edu.au/courses/comp2300/assets/manuals/nRF52833_PS_v1.7.pdf#page=756) and that page extracted with `pdftotext`. No PDF was added to the repository.

The pinned Embassy `accept_set_address` calls `accept`, which initiates EP0STATUS despite its own comment that hardware handles addressing. That is a concrete specification/source mismatch at exactly the boundary immediately after the successful addressed callback. It is **not yet demonstrated as the cause of this board's failure**: writing the extra task might be tolerated under some timing or hardware conditions, consistent with the earlier working typing image. A fix should remove only that task for SET_ADDRESS, preserving the ordinary accept path for other requests, all descriptors, clocks, interrupts and executor scheduling. Put the correction in the framework driver seam rather than duplicating USB behavior in the board code.

There is independently matching source in the bootloader's exact [TinyUSB revision, dcd_set_address](https://github.com/hathach/tinyusb/blob/9775e76910d569ec73b8dd946f3fa5fe5414acdb/src/portable/nordic/nrf5x/dcd_nrf5x.c#L257-L270): no address write or EP0STATUS task. Its [setup handler](https://github.com/hathach/tinyusb/blob/9775e76910d569ec73b8dd946f3fa5fe5414acdb/src/portable/nordic/nrf5x/dcd_nrf5x.c#L703-L711) suppresses SET_ADDRESS delivery to the stack because hardware handles it. This is source corroboration, not evidence that our vendor bootloader is byte-identical or that the correction has passed hardware testing.

The community NocFree ZMK port's resolved Zephyr commit also agrees: its [SETUP event handler](https://github.com/zmkfirmware/zephyr/blob/10ba6d0cb38bc3d258775d27982f707599320085/drivers/usb/device/usb_dc_nrfx.c#L1106-L1124) excludes standard SET_ADDRESS from software dispatch. Its [usb_dc_set_address](https://github.com/zmkfirmware/zephyr/blob/10ba6d0cb38bc3d258775d27982f707599320085/drivers/usb/device/usb_dc_nrfx.c#L1357-L1369) does not initiate status: hardware already did, and it asserts the requested address matches USBADDR. This is directly relevant port source evidence for the framework correction, not a copied transport architecture or hardware validation of our candidate.

**Revised priority:** independently review and guard a candidate with that single spec-aligned correction and the existing configured callback. A positive configured return would demonstrate progress to SET_CONFIGURATION dispatch under the corrected behavior; it would still precede its acknowledgement and would not establish usable full RMK. If it fails, retain the following instrumentation options rather than introducing speculative global-mask or polling workarounds.

## Narrow observation options if the correction does not resolve progress

There is no ordinary Handler callback between addressed and configured that universally observes a subsequent device/configuration descriptor request. `control_in` bypasses standard device requests; built-in product/manufacturer/serial strings also bypass `get_string`, which is only consulted for custom string indices. Substituting a custom string merely to invoke its callback would change descriptors and depend on host request order. [Standard control routing](https://github.com/embassy-rs/embassy/blob/50c6aac5b9b3b0af18f5a7d61725cc8e4d1f7acb/embassy-usb/src/lib.rs#L622-L647), [string routing](https://github.com/embassy-rs/embassy/blob/50c6aac5b9b3b0af18f5a7d61725cc8e4d1f7acb/embassy-usb/src/lib.rs#L719-L750).

For observation rather than a correction, a temporary diagnostic decorator around the existing Driver/ControlPipe is the smallest broadly applicable source seam: forward every operation unchanged, let SET_ADDRESS acceptance return normally, and observe the **first subsequent completed setup** without handling it. A selected standard GET_DESCRIPTOR after addressing provides stronger evidence than an unqualified setup, which might only be an address retry or another host recovery request. Comparing read-only USBADDR with the remembered nonzero address can corroborate hardware address processing; disarm on reset or mismatch to avoid stale correlation. Absence of a latched reset alone does not prove that none occurred: the framework bus poll consumes reset events, so reset handling must also explicitly invalidate the correlation. A single observation at this boundary separates subsequent setup consumption from later descriptor DMA/status/configuration progress. It still does not independently prove ISR delivery or on-wire acknowledgement. Reset only at the selected boundary via the existing reviewed serial-only route; keep this out of production firmware and do not introduce a new USB implementation.

If setup progresses but configuration does not, narrow the same decorator to completion of the relevant `data_in` operation, interpreting its result as data-stage progress rather than status acknowledgement. If setup fails, a separately reviewed diagnostic ISR observer that delegates to the standard handler could test EP0SETUP interrupt delivery, but is a more invasive next step. Observe request identity before interpreting it. Avoid a shared-join timer: it would re-poll USB and reproduce the known scheduling confound. All variants need exact-image review and fresh device/recovery gates; this note does not authorize one.

## Nordic anomalies and upstream changes

- **187 applies to nRF52833 revision 1/2** after soft/lockup reset or programming and can prevent USBD readiness. The pinned driver implements its enable bracketing. Reaching addressed dispatch in this trial argues against a total enable failure in that run. [Nordic 187](https://docs.nordicsemi.com/r/bundle/errata_nrf52833_rev2/page/err/nrf52833/rev2/latest/anomaly_833_187.html), [pinned workaround](https://github.com/embassy-rs/embassy/blob/3861d3088da30d40c777dc05d282352e68ec5511/embassy-nrf/src/usb/mod.rs#L844-L874).
- **223 applies to nRF52833 revision 1/2**, first USBD enable after reset. Nordic recommends waiting READY then disable/re-enable; its note says the failure had not been reproduced at publication. Embassy's pinned enable does not explicitly implement that cycle. Nordic nrfx does on first enable, conditionally. The installed vendor bootloader normally already enables USB before application entry, so a missing application workaround is not established as the cause. Silicon revision/vendor initialization are unmeasured; copying the sequence now would change peripheral behavior speculatively. [Nordic 223](https://docs.nordicsemi.com/r/bundle/errata_nrf52833_rev2/page/err/nrf52833/rev2/latest/anomaly_833_223.html), [nrfx at inspected revision](https://github.com/NordicSemiconductor/nrfx/blob/d1f2c35a4820961f4f7b7b2ece007f8e037842db/drivers/src/nrfx_usbd.c#L1720-L1734).
- **268 applies to nRF52833 revision 1/2**: rare transmitted-packet timing errors; control, interrupt and bulk transactions are retried, while isochronous packets can be permanently lost. Nordic's workaround is to avoid isochronous endpoints. This does not identify the deterministic enumeration failure; eventual HID latency/release acceptance still needs measurement. [Nordic 268](https://docs.nordicsemi.com/r/bundle/errata_nrf52833_rev2/page/err/nrf52833/rev2/latest/anomaly_833_268.html).
- Fresh upstream inspection found [PR 6688](https://github.com/embassy-rs/embassy/pull/6688), merged 2026-09-01. It addresses sustained bulk/interrupt OUT double-arming and adds an **nRF52840-only** anomaly-199 workaround. Its reported hardware test is nRF52840. It is relevant to future sustained CDC traffic validation, not evidence of our nRF52833 EP0 SET_ADDRESS failure. The request metadata and descriptor responses here do not use that bulk OUT completion path. A blanket upgrade or importing the 52840-only write is not justified by this trial.

No new hardware measurements, USB captures or images were made for this research. Host source inspection cannot establish USB acknowledgement, IRQ delivery, bootloader vendor behavior, or usable full RMK transport.

## Implemented experiment and software checks

The experiment pins [the published-crate patch](https://github.com/sarimabbas/embassy-nrf-nocfree/commit/9640cd7af9d2e5f9fe9860aae7108e4a04f96c8c) through Cargo's crates.io override. The source is the unchanged published Embassy nRF 0.11.0 crate except for three added lines: skip `self.accept().await` only for `nrf52833`, with a specification comment. Other chips retain their old path, and ordinary accept still issues EP0STATUS. This keeps the correction inside the framework instead of adding a board USB implementation. The normalized published manifest retains registry dependencies, so no other HAL versions or dependency sources change.

Independent byte comparison confirmed that source provenance and scope. Locked Cargo metadata resolves the patched commit; the lockfile changes only Embassy nRF's source. The repeated `./scripts/check.sh --reclaimed-softdevice` passed before and after the change: 42 Python tests, five scanner tests, two doctests, formatting, all six production role/keymap cross-builds and every existing diagnostic build. These are software checks, not hardware success. The two proposed control-pipe observer stages were saved as an ignored disposable spike and removed from the application source.

The next guarded candidate reuses `left,migration-usb-configured-serial-probe`. It preserves the existing USB descriptors, clocks, memory layout, interrupt binding, scheduling, serial-only return and independent recovery route; the framework SET_ADDRESS correction is the functional variable. Hardware is unchanged pending exact artifact review and device-specific trial approval. Full RMK left hardware startup remains unverified.
