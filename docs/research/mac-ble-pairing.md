# macOS BLE pairing after name visibility

Researched 2026-10-02. Read-only source/log analysis; no device, UI, serial or firmware actions. This note distinguishes the current host observation from possible causes. It does not establish usable Bluetooth or authorize a new image.

## What the saved host trace establishes

In the private security trace supplied for this attempt, macOS received a Just Works pairing request and accepted it. Pairing later failed with host-reported status `708`, 2.091 seconds after acceptance. The operator's earlier trace reported ATT Insufficient Encryption and a disconnect. Keep original logs and device identifiers private; they are not reproduced here.

Discovery, advertising-name visibility and pairing are distinct boundaries. This attempt got beyond the name/discovery issue and into a security procedure accepted by the host. It does **not** establish completed ECDH, matching DHKey checks, link encryption, bond persistence or HID subscription. ATT Insufficient Encryption can occur before successful pairing when an encrypted attribute is accessed; without request ordering it is not by itself an abnormal stack failure. [Trouble security documentation](https://embassy.dev/trouble/), [pinned RMK GATT/security handling](https://github.com/rmk-rs/rmk/blob/9607aedf343b17dd6b27307583ae80c4f728fbbd/rmk/src/ble/mod.rs#L490-L512).

No primary Apple mapping from the integer `708` to a specific SMP failure reason was established in this review. Do not translate it into DHKey failure, timeout, insufficient authentication, or a wire-protocol error. The trace's nearby encryption events involving another identity are not proof that this target was encrypted. An internal host status and an SMP Pairing Failed reason are separate values.

## Exact stack inspected

RMK remains pinned at `9607aedf343b17dd6b27307583ae80c4f728fbbd`. Published Trouble host 0.8.0 records upstream revision `42e3e04de00db3951b126741e1f3602bfdf5df47`; links below refer to that source, not current main. The supplied feature inspection reports `security-p256-cortex-m4`, disabled host passkey entry and SDC one-central/one-peripheral capacity. Local RMK only changes IO capabilities to KeyboardOnly when passkey entry is enabled; otherwise Trouble defaults to NoInputNoOutput. [RMK IO selection](https://github.com/rmk-rs/rmk/blob/9607aedf343b17dd6b27307583ae80c4f728fbbd/rmk/src/ble/mod.rs#L270-L275), [Trouble defaults](https://github.com/embassy-rs/trouble/blob/42e3e04de00db3951b126741e1f3602bfdf5df47/host/src/security_manager/mod.rs#L630-L650), [local role/controller selection](../../firmware/src/main.rs).

The accepted Just Works request does not support a claim that macOS rejected this device because it requires a passkey. Passkey entry remains a useful product capability for hosts requiring it, but changing IO capabilities now would alter the security procedure before identifying this failure. NoInputNoOutput produces encryption without MITM authentication; it is not equivalent to no encryption. [Official RMK pairing documentation](https://rmk.rs/main/docs/features/wireless), [Trouble security documentation](https://embassy.dev/trouble/).

## Crypto, timing and memory limits

Trouble creates a persistent LESC secret/public keypair when initialized/seeded. When a peripheral receives its peer public key, it synchronously computes the shared secret, sends its own public key and selects the pairing method. The Cortex-M4 backend validates the peer point and returns failure for an invalid/debug/same-local public key. It does not request host UI passkey confirmation for Just Works. [Initialization](https://github.com/embassy-rs/trouble/blob/42e3e04de00db3951b126741e1f3602bfdf5df47/host/src/security_manager/mod.rs#L630-L650), [DH computation](https://github.com/embassy-rs/trouble/blob/42e3e04de00db3951b126741e1f3602bfdf5df47/host/src/security_manager/crypto.rs#L398-L443), [peripheral transition](https://github.com/embassy-rs/trouble/blob/42e3e04de00db3951b126741e1f3602bfdf5df47/host/src/security_manager/pairing/peripheral.rs#L277-L303), [Just Works transition](https://github.com/embassy-rs/trouble/blob/42e3e04de00db3951b126741e1f3602bfdf5df47/host/src/security_manager/pairing/peripheral.rs#L646-L668).

Upstream [PR 641](https://github.com/embassy-rs/trouble/pull/641) reports approximately 22 ms for optimized ECDH on the author's nRF52810 benchmark and lower stack use than pure Rust; [PR 637](https://github.com/embassy-rs/trouble/pull/637) avoids recomputing the cached local public key. Both paths are already reflected in the pinned source. These are upstream measurements, not nRF52833/NocFree measurements. They do not establish either adequate runtime stack or a two-second crypto stall on our board.

The SMP timeout is 30 seconds, reset on progress. The observed 2.091-second host failure is therefore not evidence that Trouble's configured SMP timeout elapsed. A host timeout, supervision loss, cryptographic mismatch or application halt is possible, but needs its own evidence. [Timeout constant](https://github.com/embassy-rs/trouble/blob/42e3e04de00db3951b126741e1f3602bfdf5df47/host/src/security_manager/constants.rs#L5-L11), [timeout reset](https://github.com/embassy-rs/trouble/blob/42e3e04de00db3951b126741e1f3602bfdf5df47/host/src/security_manager/pairing/mod.rs#L330-L349).

This application reserves the low 32 KiB and links within the remaining 96 KiB RAM; release cross-link/image guards establish static placement only. They do not measure worst-case call stack during synchronous crypto, detect stack/data collision, or prove firmware liveness after the failure. `panic-probe` is linked with defmt printing, but there is no verified live panic/error channel for this attempt. A reset, panic or lockup hypothesis must not be called confirmed from disappearance of a BLE connection alone. [Memory map](../../firmware/memory-sdc.x), [panic dependency](../../firmware/Cargo.toml).

## Relevant upstream reports, carefully bounded

- [Trouble issue 520](https://github.com/embassy-rs/trouble/issues/520) reports an older NoInputNoOutput/Just Works state error and unconditional MITM request at a different revision. The pinned peripheral explicitly handles Just Works without numeric confirmation and derives MITM request from IO capability. That issue is not evidence the current image has the old failure.
- [PR 622](https://github.com/embassy-rs/trouble/pull/622) fixes re-pairing when a previously bonded RPA peer forgets its bond; [PR 578](https://github.com/embassy-rs/trouble/pull/578) fixes bonded RPA reconnection. These distinguish re-pairing from first pairing. The pin already uses connection-level peer-address matching and contains the relevant paths; do not assume the same old missing fix, or clear all storage without establishing stale-bond involvement.
- [Issue 115](https://github.com/embassy-rs/trouble/issues/115) is a much older macOS/iOS GATT NotFound report with different stack revisions and a long-lived connection. It is not the observed security failure. General macOS issue titles do not justify a host-stack replacement.

## Next evidence with the smallest burden

1. Verify firmware liveness immediately after the failed attempt by reattaching USB **without resetting**. Typing and normal device enumeration would weaken a whole-application halt hypothesis for the current state, while not excluding an earlier radio/security-task failure. This is an owner-assisted test for the root operator, not performed here.
2. Obtain the existing RMK `PairingFailed` error, `Encrypted` event and BLE disconnect reason for one correlated attempt through a separately validated safe observation channel. The code already logs these boundaries. Report a missing event as missing, rather than inferring one from Apple `708`.
3. If needed, capture host-side HCI/SMP packet ordering for that exact connection: pairing features, public-key exchange, confirms/randoms, DHKey checks, encryption result and Pairing Failed reason. Redact addresses and never publish encryption keys or raw security payloads. This can distinguish host cancellation, peer refusal, crypto failure and disconnect timing without changing IO capabilities or replacing Trouble.
4. Only after the failing boundary is known, propose one narrowly matched correction, with the existing recovery/readback gates. A software crypto self-test can reject known-answer failures but is not pairing hardware acceptance; cross-builds cannot establish dynamic stack safety or BLE scheduling.

Do not switch to NimBLE, toggle unrelated PHY/security flags or fork broad stack behavior merely because host pairing failed. The next useful result is a correlated failure boundary or firmware liveness observation.

After the owner followed the retained-image battery-first startup sequence, the left enumerated normally as `NocFree RMK Left`, with no bootloader present. No firmware was written or restored during these observations. The same installed application can still start; the failing pairing boundary remains unknown.

The smallest available closed-board error channel is pinned RMK `usb_log`, which adds its existing CDC logger alongside USB HID. The installed image uses RTT only. A separately guarded logging candidate must preserve normal production defaults. An initial Info-level cross-build exceeded the application flash boundary by 3,200 bytes. Warning-level logging retains `PairingFailed` diagnostics while omitting normal connection/encryption milestones and Info pairing-code prompts; Trouble Trace output can include security material. Warning-level USB logging can report ordinary pairing errors and runner failures, but cannot guarantee panic output because the panic handler disables interrupts. Preparing this candidate is software work, not approval to install or open its serial channel.

The Warning-level cross-build fits the unchanged application partition (linked flash end `0x63ee4`, 4,380 bytes before `0x65000`). It is not installed or hardware validated. Independent review found two material limitations: RMK hashes its enabled features into the settings schema, so switching logging modes can erase/reinitialize stored split peers and host bonds; and Trouble can emit cryptographic confirm values at Error level on a confirm failure, so even Warning-level captures must remain private and be redacted. Neither the image address guard nor the log filter proves settings preservation or absence of sensitive output. No schema override or framework fork was added.

The next-build host product name is `NocFree RMK`, reflecting that the left coordinator presents the entire keyboard. The installed image and observations above still use `NocFree RMK Left`. This string change does not alter the RMK storage schema; the optional logging feature change separately does.

Offline validation passed before and after the logging feature changes: 42 image/package host tests, seven scanner host tests, and all six production role/keymap cross-builds plus the diagnostic builds. The warning logger retains pairing/runner errors but omits ordinary disconnect reasons (Info). Its 1,024-byte buffer can drop or truncate data, so missing output cannot prove absence of a failure. Independent review passed the feature scope; installation and hardware logging remain unapproved/unverified.

The offline candidate with whole-keyboard name has BIN size 405,220 bytes and page-padded coverage `0x1000..0x64000`; application vectors are SP `0x20020000`, Thumb reset `0x1205`. `inspect_migration` passes exact payload/vector/family/recovery-marker checks.
