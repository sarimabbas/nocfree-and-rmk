# USB startup boundaries after the HAL trial

Research on 2026-10-01; software preparation only. No new image is authorized for installation by this document. The [runtime/HAL trial](runtime-hal-trial.md) returned to readable DFU after both controlled battery-first sequences and restored the original factory image exactly. Those observations are consistent with reaching each reset boundary, not independent execution proof. The earlier complete lower-layout USB probe remained silent. A root cause is still unknown.

## Exact primary sources

The local published crates record these upstream revisions in `.cargo_vcs_info.json`: embassy-nrf 0.11.0 = `3861d3088da30d40c777dc05d282352e68ec5511`; embassy-usb 0.6.0 = `50c6aac5b9b3b0af18f5a7d61725cc8e4d1f7acb`. Findings below come from those local crate files, with upstream source links at the same revisions. They are not claims about current Embassy main.

## Smallest useful candidates

1. **Driver constructed:** return to the existing DFU immediately after the unchanged combined `Driver::new(..., HardwareVbusDetect::new(...))` expression. This separates the interrupt-enabling constructors from the observed HAL boundary. If it fails, split VBUS and USBD constructor boundaries next; do not preemptively normalize interrupt or peripheral state.
2. **Device built:** return immediately after unchanged `Builder::build`, before CDC splitting/run tasks. Keep actual descriptor/class allocation intact. Independent optimized-ELF review must establish that the intended constructor/build work survives the diverging reset; syntactic placement is insufficient.
3. **USB enable completed:** register a normal Embassy Handler and return only from `enabled(true)` while retaining the original USB run path. This is a framework-supported callback, without a custom driver or poll wrapper. It delimits the asynchronous READY/power waits but cannot distinguish their individual failures or prove the pullup connected.
4. **Host configuration request handled:** same framework Handler, return only from `configured(true)`. If enable-completed returns but this does not, investigate attach/control handling rather than treating that result as proof of an IRQ root cause. A later complete USB/CDC greeting trial is still necessary.

Constructor/build probes reset before USB is attached in the battery-first launch. Callback probes normally keep the application running while USB is absent, then reset only after attachment produces the relevant event. Their observation schedule must account for this difference; an absent drive before attachment is expected for callback probes. A drive visible afterward remains only consistent with reaching the selected boundary because bank validity, the recovery marker and vendor bootloader behavior are independent alternatives.

Use the same reviewed volatile GPREGRET/DSB/system-reset helper, exact role guards and existing recovery marker. For tiny linked images retain the explicit erased-word extent after `.text`; preserve Cortex-M data/BSS symbols and reconstruct exact ELF load bytes before packaging. Larger callback images must pass the same migration address/family/vector guard without weakening it. Verify their actual touched pages and factory retained ranges; do not assume the previous three-page bounds. Never invoke the reset helper for false/disable/unconfigure callbacks.

## Hypotheses to test, not diagnoses

- **Interrupt handoff:** READY and POWER waits use IRQ-triggered wakers. USBD/POWER constructors unpend and enable the relevant NVIC lines, but that is not evidence that global CPU interrupt masks or leftover peripheral interrupt sources are suitable. The constructor stage detects failures around enabling those lines; enable completion tests later wakes. An inherited mask/state issue is a hypothesis, not an observed fact. [USBD ISR:37–79](https://github.com/embassy-rs/embassy/blob/3861d3088da30d40c777dc05d282352e68ec5511/embassy-nrf/src/usb/mod.rs#L37-L79), [POWER ISR:55–90](https://github.com/embassy-rs/embassy/blob/3861d3088da30d40c777dc05d282352e68ec5511/embassy-nrf/src/usb/vbus_detect.rs#L55-L90).
- **Peripheral handoff:** Driver construction does not reset USBD. Enable uses the READY event and published nRF errata sequence; prior vendor state could matter, but no register capture currently establishes it. Do not add a custom disable/reset workaround until a boundary observation supports investigating that seam. [enable and errata source](https://github.com/embassy-rs/embassy/blob/3861d3088da30d40c777dc05d282352e68ec5511/embassy-nrf/src/usb/mod.rs#L846-L875).
- **Power/wakeup:** Native VBUS detection reads current POWER status and awaits output-ready rather than requiring a newly observed detection edge. Thus an already-present cable alone is not sufficient evidence of a missed-event bug. A lost IRQ wake or persistent power-not-ready remains possible; initial and later polls differ. [native status/wait source](https://github.com/embassy-rs/embassy/blob/3861d3088da30d40c777dc05d282352e68ec5511/embassy-nrf/src/usb/vbus_detect.rs#L145-L182).
- **Clocks:** The HAL candidate retains the external-HFXO initialization and default LF clock. Its recovery observation does not measure clock state or prove USB timings. These proposed candidates keep clock configuration unchanged.

No watchdog, GPIO indicator, flash log, bootloader replacement, UICR write, generic runner or interrupt-mask workaround is proposed. Host harnesses and cross-builds verify software only. Hardware transfer requires a separately reviewed artifact, fresh device evidence and explicit trial approval, with original factory restoration included.

## Distinct serial-mode control before asynchronous probes

The previous `0x57` stage-return probes share MSC behavior with marker-driven bootloader entry. A stronger comparison is to prepare a HAL control and post-build candidate that request **`0x4e` serial-only DFU** at their respective boundaries, retaining the independent `0x57`/recovery-marker path. Upstream 0147d71 defines `0x4e` separately, derives `serial_only_dfu` directly from GPREGRET, and passes that mode to `usb_init`; marker entry independently requests DFU without setting serial-only mode. [main.c:81–107](https://github.com/adafruit/Adafruit_nRF52_Bootloader/blob/0147d71e73b9a2c217f56dbc9877d07bb45d6467/src/main.c#L81-L107), [205–243](https://github.com/adafruit/Adafruit_nRF52_Bootloader/blob/0147d71e73b9a2c217f56dbc9877d07bb45d6467/src/main.c#L205-L243), [267–285](https://github.com/adafruit/Adafruit_nRF52_Bootloader/blob/0147d71e73b9a2c217f56dbc9877d07bb45d6467/src/main.c#L267-L285).

This is a vendor-behavior assumption until calibrated on this installed bootloader and lower layout. [Earlier device research](hardware.md#live-serial-only-entry-observed-during-this-session) records serial-only entry from the left factory application, not a direct measurement of its GPREGRET write or a calibrated replacement-image response. Require a correlated serial bootloader identity **and absence of MSC**, rather than treating any USB reappearance as the requested signal. HAL-serial is the control for whether the mode distinction works; do not interpret the build-stage result if that control fails to distinguish modes.

A post-build probe must keep the actual configured CDC descriptor construction and observe its result (for example with `core::hint::black_box(&mut device)`) before the diverging reset. Verify optimized instructions retain both USB interrupt enables and descriptor/build work. The control remains before driver construction. This pair does not run USB, test wakers, or enumerate the application; it improves the specificity of the return signal before those larger steps. Neither the research nor source preparation authorizes another hardware transfer.
