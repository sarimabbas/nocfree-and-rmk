# Upstream BLE failure review

Reviewed 2026-10-02, using current GitHub issue/PR state and the exact local Cargo sources. This is read-only research: no firmware, helper, device, serial, or pairing changes. It does not establish the cause of the owner's failed pairing.

## What is already present

Our RMK pin is `9607aedf343b17dd6b27307583ae80c4f728fbbd` (2026-09-30). Cargo resolves Trouble Host 0.8.0, whose published source identifies commit `42e3e04de00db3951b126741e1f3602bfdf5df47`; nRF SDC 0.4.0 identifies `e44e619d15eba9145453e3b2d7b07121556871ab`. The [Trouble 0.8 release](https://github.com/embassy-rs/trouble/releases/tag/trouble-host-v0.8.0) already includes:

- [PR 630](https://github.com/embassy-rs/trouble/pull/630), merged June 22: guards against one link's SMP/encryption events reaching another link's state machine. Published `security_manager/mod.rs` has `pairing_sm_for` and regression tests for encryption while a different peer owns that state machine.
- [PR 651](https://github.com/embassy-rs/trouble/pull/651), merged August 18: processes SMP received before the application accepts a connecting link.
- [PR 637](https://github.com/embassy-rs/trouble/pull/637), merged July 6: avoids recalculating the local public key during ECDH.
- [PR 641](https://github.com/embassy-rs/trouble/pull/641), merged August 17: introduces the Cortex-M4 optimized P-256 backend. Our [RMK `_nrf_ble` feature](https://github.com/rmk-rs/rmk/blob/9607aedf343b17dd6b27307583ae80c4f728fbbd/rmk/Cargo.toml) already enables it. The author's benchmark reports approximately tenfold pairing-computation improvement on their target; that is not a timing measurement of our keyboard.

Consequently, “enable accelerated crypto,” “accept early SMP,” and “add cross-peer guards” are not missing fixes in this build. Open [issue 603](https://github.com/embassy-rs/trouble/issues/603) describes a bonded multirole crash, but its title alone does not show our release lacks the corresponding guards. Our saved right split record is a peer address, not a bond; the saved left snapshot before host pairing contained no host bond.

## Changes after the pins

At review time, [Trouble main compared with 0.8.0](https://github.com/embassy-rs/trouble/compare/trouble-host-v0.8.0...730198ecf94ee6953163b7485cf902d5f9d45dbd) was 13 commits ahead. Relevant merged fixes include [PR 688](https://github.com/embassy-rs/trouble/pull/688), September 25: cleans stale disconnect slots, recycled handles and undelivered disconnect events. It targets connection churn, not specifically fresh Mac Just Works pairing. Other changes include ReadEvent response length, an embassy-crypto refactor, and reporting failed PHY/connection-parameter updates. A wholesale upgrade would mix these changes and require RMK API/build/storage review.

[RMK main compared with our pin](https://github.com/rmk-rs/rmk/compare/9607aedf343b17dd6b27307583ae80c4f728fbbd...92a626cf5f836f1ecb1581af5b773fe94b7e9938) was 24 commits ahead. Those changes expose profile bond status and address configuration/macros/ADC/tooling; the comparison supplies no identified Mac first-pairing fix. [nRF SDC main](https://github.com/alexmoon/nrf-sdc/commit/e44e619d15eba9145453e3b2d7b07121556871ab) equals our published revision, so there is no newer upstream commit there to apply.

## Ranked hypotheses and rejection tests

These ranks describe research priority, not probability or a diagnosis. The observed facts remain: the short-name image advertises; macOS accepted Just Works and then failed with opaque status 708; host HID registration was not observed; a later restart returned USB. The logger image's later USB absence is a separate startup observation and cannot retrospectively prove a pairing panic.

| Priority | Candidate mechanism | Evidence and limits | Safest next offline check |
| --- | --- | --- | --- |
| 1 | Pairing crypto/address encoding or backend defect | Open [PR 660](https://github.com/embassy-rs/trouble/pull/660) demonstrates failed LESC when identity address kinds `0x02/0x03` are used directly in f5/f6. Published 0.8 `Address::to_bytes` preserves the kind; crypto consumes it. No observed HCI peer address type or DHKeyCheckFailed here. Fresh, unresolved public/random addresses would disfavor this case. | Run pinned crypto known-answer vectors and an isolated identity-kind encoding test; compare public/random against identity aliases. This can confirm a source defect but cannot establish that our Mac exercised it. Retain the actual error boundary as the deciding evidence. |
| 2 | Runner termination following a late encryption event, or unmatched LTK request | Open PR 660 also proposes tolerating an encryption event after disconnect and negative-reply handling for missing LTKs. It documents ESP32/BlueZ tests and an HCI shim, not our nRF/Mac. A host could retain a bond while the keyboard has none; the keyboard snapshot alone cannot exclude host state. | Reproduce those event sequences against the pinned state machine with a fake HCI transport. An actual LTK request/error or runner-stop record is needed before selecting either correction. |
| 3 | Link/connection-slot cleanup under multirole churn | PR 688 addresses stale slots and recycled handles. Our left has one split-central link and one host-peripheral link, so this area matters, but basic split input works and the reported failure was initial host pairing, not demonstrated churn. | Replay disconnect/reused-handle/full-event-queue sequences against 0.8 and the narrow upstream fix. Do not add application delays or a second transport manager. |
| 4 | Stack pressure or crypto scheduling | Optimized P-256 is enabled already; the logger ELF retains 32,128 bytes between `__sheap` and initial SP, versus 33,744 previously. Static headroom does not prove maximum stack use or interrupt timing. | Inspect actual linked crypto symbols and known-answer tests; compare static/stack estimates. Only measured device behavior can establish wake/latency safety. |
| Low | Missing LESC capability / IO policy | Pinned NoInputNoOutput selects Just Works; legacy pairing is disabled. The host accepted Just Works, which argues against a missing PIN UI being the sole explanation. No captured AuthReq permits a legacy-compatibility conclusion. | Compare the pinned feature/request negotiation tests. Do not enable legacy pairing or change IO capabilities without the failing SMP request/reason. |

[Issues 689](https://github.com/embassy-rs/trouble/issues/689) and [691](https://github.com/embassy-rs/trouble/issues/691), both open against 0.8, concern central-side **bonded re-encryption**. They are useful future reconnect acceptance cases, but do not directly match a first host pairing where our keyboard is the peripheral and the split link has no saved bond.

## Older reports and bootloader lessons

[Issue 372](https://github.com/embassy-rs/trouble/issues/372) describes an iOS encrypted-read pairing panic with an insufficient packet MTU. It was closed after the April 2025 main-branch fix; it is not evidence that current 0.8 still has that bug. [Issue 115](https://github.com/embassy-rs/trouble/issues/115) is a 2024 Apple connection/controller report. Maintainers requested a sniffer and identified possible oversized/incorrectly segmented traffic; it supplies no mapping from our Apple status 708 to a Nordic assertion.

Open [nRF SDC issue 103](https://github.com/alexmoon/nrf-sdc/issues/103) and closed, unmerged [Trouble PR 694](https://github.com/embassy-rs/trouble/pull/694) discuss bootloader/nonzero-origin startup. The PR author reports a different nRF52840/S140 layout working with `set-vtor`. These are comparison material, not permission to change our proven recovery route or erase MBR/S140/bootloader. Our own earlier full USB and split operation is stronger board-specific evidence than a generic claim that MPSL cannot work behind an MBR.

The most useful path is to reject precise source hypotheses offline while preserving the installed checkpoint, then obtain one correlated firmware failure boundary when the owner returns. Neither a repository success story nor a passing host harness demonstrates reliable Mac pairing, disconnect recovery, simultaneous input or latency on this board.

## Runner error, recovery marker and rediscovery interaction

Our pinned [RMK BLE runner](https://github.com/rmk-rs/rmk/blob/9607aedf343b17dd6b27307583ae80c4f728fbbd/rmk/src/ble/mod.rs#L434-L442) already logs a runner error, waits 100 ms, and calls `reboot_keyboard`; it does **not** panic on that return. [RMK boot code](https://github.com/rmk-rs/rmk/blob/9607aedf343b17dd6b27307583ae80c4f728fbbd/rmk/src/boot.rs) performs an ordinary system reset for that call. Unlike explicit `jump_to_bootloader`, it does not set GPREGRET to the UF2 request. PR 660's late-encryption-event hypothesis would therefore predict a framework reboot here rather than its example application's panic. It is still unmerged and not included in 0.8.

The unchanged image marker is interpreted by the reported upstream [bootloader `main.c`](https://github.com/adafruit/Adafruit_nRF52_Bootloader/blob/0147d71e73b9a2c217f56dbc9877d07bb45d6467/src/main.c#L205-L291). Its single-tap convention enters a three-second DFU window unless the retained application-start marker requests immediate startup; main clears that retained word before jumping to the application. USB enumeration can keep that DFU window open. Thus an application-triggered ordinary reset can plausibly become a bootloader wait when USB is attached, or another application attempt after a battery-only timeout. This is an upstream path and an inference about the vendor bootloader; no reset reason or runner error has been observed in this trial. Neither a reboot loop nor an application panic follows from USB absence alone.

The logger feature change resets **left** stored peer addresses. The right retains a peer address for the same left BLE address, not a cryptographic split bond. Pinned [right split code](https://github.com/rmk-rs/rmk/blob/9607aedf343b17dd6b27307583ae80c4f728fbbd/rmk/src/split/ble/peripheral.rs#L213-L300) uses its stored coordinator address for directed advertising, with a timeout followed by ordinary split advertising. Pinned [left split code](https://github.com/rmk-rs/rmk/blob/9607aedf343b17dd6b27307583ae80c4f728fbbd/rmk/src/split/ble/central.rs#L45-L176) scans when its peer slot is empty and persists a discovered address. A unilateral left reset therefore predicts rediscovery work, not a stale-LTK failure by itself. No linked source shows an expected loss of the USB interface merely because the left peer slot is empty. A replay of empty-left/stored-right discovery plus runner-error/reset ordering is a useful offline rejection test; hardware rediscovery remains unverified after this update.
