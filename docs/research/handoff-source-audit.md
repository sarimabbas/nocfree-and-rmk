# Working versus reclaimed startup: source audit

Reviewed 2026-10-02. Source inspection only: no builds, device commands, writes, or port actions. The installed bootloader reports upstream base `0147d71`; its private vendor changes and resident MBR implementation remain unverified. The earlier S140-preserving USB typing result and recent reset-callback result are supplied hardware observations, not reproduced by this review.

## Concrete difference

| Boundary | S140-preserving application (`0x27000`) | Reclaimed application (`0x1000`) |
| --- | --- | --- |
| Bootloader main | Detects S140, initializes its MBR path if necessary, and disables the SoftDevice before entry | Omits those S140 operations |
| Interrupt forwarding | Requests the SoftDevice vector-table base at the dynamic application address | Requests runtime MBR IRQ forwarding at `MBR_SIZE` |
| Common entry | Clears NVIC enable/pending banks, then loads application's MSP and Reset vector | Same common entry |
| Rust startup | `set-vtor` establishes the application's own vector base | Same runtime feature at the lower address |
| Probe USB HAL | External HFXO, USBD binding, CLOCK_POWER binding, HardwareVbusDetect | Same source choices |

These distinct forwarding routes are explicit in [bootloader main](https://github.com/adafruit/Adafruit_nRF52_Bootloader/blob/0147d71e73b9a2c217f56dbc9877d07bb45d6467/src/main.c#L174-L200) and [application startup](https://github.com/adafruit/Adafruit_nRF52_Bootloader/blob/0147d71e73b9a2c217f56dbc9877d07bb45d6467/lib/sdk11/components/libraries/bootloader_dfu/bootloader.c#L349-L393). Failed forwarding falls back to writing the application base to SRAM's first word. The application RAM floor preserves that word. No persistent MBR vector command is needed or proposed.

**Origin is not the only changed variable.** Working `input-probe.rs` joins the scanner, keyboard and USB inside the same task. [RMK's run_all macro](https://github.com/rmk-rs/rmk/blob/9607aedf343b17dd6b27307583ae80c4f728fbbd/rmk/src/input_device/mod.rs#L81) expands through [join_all](https://github.com/rmk-rs/rmk/blob/9607aedf343b17dd6b27307583ae80c4f728fbbd/rmk/src/helper_macro.rs#L5-L14) to Embassy's join combinator. The installed [embassy-futures `0.1.2` join implementation](https://github.com/embassy-rs/embassy/blob/3e8d8fec15286eb25b8bba7d103c8fc279544551/embassy-futures/src/join.rs#L87-L103) polls every unfinished child whenever the parent is polled. The scanner's 1 ms timer after each scan therefore causes USB to be polled repeatedly, even if a USB-specific wakeup were missing. The recovery probe has no comparable timer before configuration: its greeting waits for connection before starting timed waits. This is a source-backed scheduling confound, not proof that wakeups are actually broken. It means the working input result alone cannot isolate the flash layout as the cause or establish interrupt delivery. Do not add periodic USB polling as an unexplained production workaround.

## Voyager hypotheses checked

**Inherited CPU masks remain an observation question.** The [GCC handoff](https://github.com/adafruit/Adafruit_nRF52_Bootloader/blob/0147d71e73b9a2c217f56dbc9877d07bb45d6467/lib/sdk11/components/libraries/bootloader_dfu/bootloader_util.c#L66-L104) changes MSP and branches, with handler-mode exit support; it does not explicitly normalize PRIMASK, BASEPRI or CONTROL. NVIC bank clearing is not global mask clearing. Inspection did not find a normal no-S140 path that demonstrably leaves those masks wrong. Vendor hooks, MBR code and library internals limit that conclusion.

The pinned [MPSL critical-section implementation](https://github.com/alexmoon/nrf-sdc/blob/e44e619d15eba9145453e3b2d7b07121556871ab/nrf-mpsl/src/critical_section_impl.rs) temporarily masks globally, preserves incoming PRIMASK, and saves/restores ordinary NVIC enables while excluding reserved radio IRQs. It does not initialize MPSL or call its radio API. It would preserve an inherited bad global mask, but does not establish one. Replacing it or copying Voyager's mask normalization now would be a hypothesis-driven change, not a known fix.

**An inherited USB attachment is not supported by the ordinary upstream teardown path.** Returning non-OTA DFU calls [usb_teardown](https://github.com/adafruit/Adafruit_nRF52_Bootloader/blob/0147d71e73b9a2c217f56dbc9877d07bb45d6467/src/usb/usb.c#L98-L101). That synthesizes TinyUSB's power-removed event. The bootloader's exact [TinyUSB submodule](https://github.com/adafruit/Adafruit_nRF52_Bootloader/tree/0147d71e73b9a2c217f56dbc9877d07bb45d6467/lib) is `9775e76910d569ec73b8dd946f3fa5fe5414acdb`; its [removal handler](https://github.com/hathach/tinyusb/blob/9775e76910d569ec73b8dd946f3fa5fe5414acdb/src/portable/nordic/nrf5x/dcd_nrf5x.c#L1001-L1021) synchronously clears USBPULLUP, disables USBD NVIC and peripheral interrupts, disables USBD and releases HFXO when the peripheral is enabled. This weakens a direct Voyager detach patch. Actual vendor register state is still unmeasured.

## What the reset callback establishes

The pinned [Embassy driver](https://github.com/embassy-rs/embassy/blob/3861d3088da30d40c777dc05d282352e68ec5511/embassy-nrf/src/usb/mod.rs) enables USBD interrupts and waits for peripheral READY and power-ready before connecting its pull-up. Its bus poll reads USBRESET directly. Consequently, a successful framework reset callback proves that software observed a reset event; it does not independently prove USBD ISR delivery.

EP0 setup also reads a register, but an event arriving after its future sleeps needs a wakeup. The USBD handler supplies that wakeup. Configuration occurs later than the first setup and descriptor exchanges. Missing configuration therefore leaves several boundaries unresolved. The corrected ExternalXtal path already clears the start event and starts HFXO; repeating a stale-clock workaround is unjustified by the present evidence.

## Ranked next single observation

Prefer **the standard `Handler::addressed` callback** for the next guarded observation. [Embassy's SET_ADDRESS handling](https://github.com/embassy-rs/embassy/blob/50c6aac5b9b3b0af18f5a7d61725cc8e4d1f7acb/embassy-usb/src/lib.rs#L501-L545) recognizes a standard device request with address 1 through 127, stores the pending address/state and invokes the callback. Only after it returns does the outer control handler request `accept_set_address`; the nRF driver implements that with EP0STATUS. Returning to recovery inside the callback proves that a legal SET_ADDRESS SETUP reached framework dispatch, **before its status-stage acknowledgement**, without duplicating the driver. It does not prove address commitment, complete descriptor exchange or IRQ delivery. Hosts commonly request initial descriptors before addressing; callback success itself cannot establish the host's exact order.

If that boundary fails, observing the first USBD interrupt with EP0SETUP set would discriminate interrupt delivery from framework control progress more directly, but requires separately reviewed diagnostic instrumentation outside ordinary callbacks. CPU-mask/CONTROL/VTOR capture at an existing callback is another possible observation only after establishing a safe retained-state readback channel. Neither instrumentation nor normalization is implemented or authorized by this source audit.

Do not use ordinary `Handler::control_in` as a first-device-descriptor hook: [Embassy's standard control dispatch](https://github.com/embassy-rs/embassy/blob/50c6aac5b9b3b0af18f5a7d61725cc8e4d1f7acb/embassy-usb/src/lib.rs#L622-L711) handles standard device GET_DESCRIPTOR before delegating to handlers. An absent handler callback would be expected and would misdiagnose the failure. Any diagnostic wrapper must remain narrowly scoped, preserve the same guarded image/recovery route, and receive independent review before proposing a hardware trial.
